# Hybrid RAG — O'zbekiston qonunchiligi (Uzbek Law)

A fully local, offline Hybrid Retrieval-Augmented Generation system for
answering legal questions in Uzbek, grounded in the actual text of Uzbek
legal codes (no cloud APIs, no external services after setup).

> **Status:** All 20 milestones complete. Every page in the spec's
> navigation is real; the system indexes, retrieves, reranks, generates,
> and cites sources end to end, fully offline after setup.

## Why "hybrid"?

Retrieval combines two complementary search strategies:
- **Dense retrieval** (FAISS + multilingual sentence embeddings) — good at
  matching *meaning* even when wording differs from the source text.
- **Sparse retrieval** (BM25) — good at matching *exact legal terms and
  article numbers*, which dense embeddings can blur.

Results from both are fused, then reranked with a cross-encoder for a final
precision pass before being handed to a local LLM (via Ollama) to generate
a grounded, cited answer.

## How a question becomes an answer

```
User Question
   │
   ▼
Query preprocessing        (app/rag/query_processing.py — trim, length-cap, reject empty)
   │
   ▼
Hybrid retrieval            (app/retriever/ — FAISS dense + BM25 sparse, min-max
   │                         normalized and fused by DENSE_WEIGHT/SPARSE_WEIGHT)
   ▼
Cross-encoder reranking     (app/reranker/ — a second, more accurate pass over
   │                         the fused candidates)
   ▼
Context compression         (app/rag/context_compression.py — drop near-duplicate
   │                         chunks, enforce MAX_CONTEXT_CHARS)
   ▼
Prompt construction         (app/prompts/ — Uzbek system prompt, numbered
   │                         source blocks, mandatory "not found" fallback)
   ▼
Local LLM (Ollama)          (app/llm/ollama_client.py)
   │
   ▼
Answer + cited sources      (law name, article number, page, similarity/rerank scores)
```

`app/rag/pipeline.py`'s `RAGPipeline` is the one class that wires every
stage together — see its own docstring for why `retrieve()` (no LLM call)
and `ask()`/`ask_stream()` (full answer) are separate public methods.

## Corpus

`documents/raw/` ships with five Uzbek legal codes as plain text:

| File | Code |
|---|---|
| `fuqorolik.txt` | Fuqarolik kodeksi (Civil Code) |
| `fuqorolik_protsessual.txt` | Fuqarolik protsessual kodeksi (Civil Procedure Code) |
| `iqtisodiy_protsessual.txt` | Iqtisodiy protsessual kodeksi (Economic Procedure Code) |
| `jinoyat.txt` | Jinoyat kodeksi (Criminal Code) |
| `mehnat.txt` | Mehnat kodeksi (Labor Code) |

New documents (PDF, DOCX, TXT, HTML) can be added anytime via the **Hujjat
yuklash** (Upload) page without touching any code, then indexed from
**Indeksni boshqarish** (Index management).

## Setup

```bash
cd hybrid_rag
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # then edit .env if you want non-default models

python run.py                      # validates config, then launches the Streamlit UI
```

`python run.py` opens the app at http://localhost:8501. On first launch the
index is empty — open **Indeksni boshqarish** and click **Indeksni qurish /
yangilash** to index everything under `documents/raw/` (a few thousand
chunks takes well under a minute on a laptop CPU; the first run also pays a
one-time embedding-model download/load cost).

### Local LLM (Ollama)

This project generates answers with a model served locally by
[Ollama](https://ollama.com). Install Ollama, then pull a model:

```bash
ollama pull llama3.2:3b            # or qwen2.5, mistral, gemma2, deepseek-r1 ...
```

Set `LLM_MODEL` in `.env` to match whichever tag you pulled. Every page
except **Statistika** requires `ollama serve` to be running (Statistics
reads only files already on disk — see `app/ui/pages/statistics.py`'s
docstring for why it was deliberately built to need neither Ollama nor a
loaded embedding model just to be viewed).

### A note on RAM and the embedding model

The project's original design spec named `BAAI/bge-m3` (~2.3GB of weights,
needing roughly double that in RAM transiently while loading) as the
example embedding model. On this project's own 8GB-RAM development
machine, loading `bge-m3` hung indefinitely on `EMBEDDING_DEVICE=mps` and
thrashed (severe swapping, 10+ minutes without completing) on
`EMBEDDING_DEVICE=cpu` — the machine was already low on free RAM, and a
multi-GB model load pushed it into swap. This is a resource constraint,
not a bug.

Because of that, **the default `EMBEDDING_MODEL` in this project is the
much lighter `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
(~470MB)**, which loaded quickly and correctly on the same machine and is
what the test suite uses. If you have more RAM headroom (16GB+
recommended) and want better retrieval quality, switch `EMBEDDING_MODEL`
in `.env` to `BAAI/bge-m3` or `intfloat/multilingual-e5-large` — both are
fully supported (see `app/retriever/embeddings.py`'s docstring for how
query/document text formatting is handled automatically per model
family). If you try a heavier model and hit the same hang/thrashing:
- Close other memory-heavy applications before the first load.
- Prefer `EMBEDDING_DEVICE=cpu` over `mps` — `mps` produced an outright
  hang in testing, `cpu` at least made (slow) forward progress.
- `intfloat/multilingual-e5-base` (~1.1GB) is a reasonable middle ground.

### A note on small local LLMs and citation reliability

The default `LLM_MODEL`, `llama3.2:3b`, is small (3B parameters) and can
occasionally produce self-contradictory answers — e.g. opening with the
"I could not find this information" fallback phrase and then pasting the
retrieved sources verbatim right after it anyway. This was observed
during testing with a sparse retrieved context, and did not reproduce
across repeated tries against the full real corpus with realistically-
sized chunks — see `app/llm/ollama_client.py`'s docstring for the full
investigation. If you see garbled or contradictory answers in practice,
the most direct fix is a larger model: `qwen2.5:7b` or similar, RAM
permitting (see the embedding-model RAM note above for this project's own
constraints). This is a model-capability limitation, not a bug in the
prompt or pipeline code.

## The UI

7 pages, grouped in the sidebar:

| Page | What it does |
|---|---|
| **Bosh sahifa** (Home) | System status at a glance — corpus size, Ollama connectivity, indexed laws, quick links. |
| **Suhbat** (Chat) | Ask questions in Uzbek; streamed answers, source cards with dense/sparse/combined/rerank scores, copy/download, chat history. |
| **Hujjat yuklash** (Upload) | Drag-and-drop PDF/DOCX/TXT/HTML, multiple files, progress bar, safe overwrite handling. |
| **Indeksni boshqarish** (Index management) | Build/update (always incremental), rebuild from scratch, or delete the index — destructive actions require a two-step confirmation. |
| **Qidiruv tahlili** (Retrieval Debug) | Run a query and see every candidate chunk's full score breakdown and compression outcome — the "why did this show up" transparency tool. |
| **Statistika** (Statistics) | Corpus/index/memory numbers — document and chunk counts, per-law breakdown, embedding dimension, FAISS/BM25/SQLite sizes, process RSS. |
| **Sozlamalar** (Settings) | Read-only view of the current `.env`-driven configuration, plus an on-demand Ollama connectivity check. |

## Configuration

All configuration lives in `.env` (see `.env.example` for every key and its
default). Highlights:

| Variable | Purpose |
|---|---|
| `LLM_MODEL` | Ollama model tag used for generation |
| `EMBEDDING_MODEL` | Multilingual embedding model for dense retrieval |
| `RERANKER_MODEL` | Cross-encoder used to rerank hybrid results |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | Text splitting parameters |
| `TOP_K` / `RERANK_TOP_K` | Candidates before/after reranking |
| `DENSE_WEIGHT` / `SPARSE_WEIGHT` | Hybrid score fusion weights |
| `VECTOR_PATH` / `BM25_PATH` / `SQLITE_PATH` | Where indexes/metadata are stored |

The **Sozlamalar** page shows every current value live; changing `.env`
requires a process restart (see that page's docstring for why it's
read-only rather than a live editor).

## Testing

```bash
python -m pytest                        # full suite
python -m pytest tests/test_chunker.py   # one file
python -m pytest -k "not page"           # skip the slower Streamlit AppTest suites
```

The suite favors real components over mocks wherever the real component is
fast and deterministic enough to use directly (the actual chunker, the
actual SQLite repository, the actual FAISS/BM25 indexes over small
in-memory corpora) — mocks are reserved for genuinely external, slow, or
non-deterministic dependencies (Ollama's HTTP calls). A handful of tests
(`test_chat_page.py`, `test_retrieval_debug_page.py`,
`tests/evaluation/test_retrieval_evaluation.py`) deliberately run against
this project's own real, already-indexed corpus rather than an isolated
fixture — see each file's docstring for why that's representative
behavior, not test pollution. Those specific tests need the real corpus
indexed first (**Indeksni boshqarish** → **Qurish / yangilash**, or run
`IndexingPipeline().sync()` directly) and, for the Chat/Debug page tests,
a running `ollama serve` with `LLM_MODEL` pulled.

### Retrieval evaluation

```bash
python -m pytest tests/evaluation/ -v
```

`tests/evaluation/` measures retrieval quality directly, using the four
standard information-retrieval metrics: **Precision@K**, **Recall@K**,
**MRR**, and **nDCG@K** (implementations in `app/rag/evaluation.py`,
docstring covers each metric's definition and the design decisions behind
them — including why relevance is graded at the article level rather than
the chunk level, and why the metric formulas are hand-implemented rather
than delegated to a library, cross-checked against `scikit-learn`'s
reference `ndcg_score` in `test_retrieval_metrics.py`).

`tests/evaluation/golden_dataset.py` holds 8 hand-verified (query →
relevant article) pairs — one per legal code at minimum, each built by
`grep`-ing the real source text for a distinctive fact and phrasing a
natural Uzbek question about it, not synthetically generated. Running it
against the current index reports (with default settings):

| Metric | Score |
|---|---|
| Precision@5 | 0.20 (ceiling — exactly 1 relevant article per query, in 5 slots) |
| Recall@5 | 1.00 |
| MRR | 0.70 |
| nDCG@5 | 0.77 |

`test_retrieval_evaluation.py` asserts these stay above a floor (not a
perfect score — see that file's docstring on why the threshold is
deliberately loose for an 8-query sample) as a regression guard: if a
future change to chunking, the embedding model, or fusion weights drops
retrieval quality, this test catches it. One golden query's evolution is
worth reading about directly in `golden_dataset.py`'s comments: an earlier
phrasing failed outright because it used a different Uzbek grammatical
case of the key word than the source text (BM25 does no stemming, and the
small MiniLM embedding model's semantic similarity also missed it) — a
real, documented limitation of this project's lightweight default models
on Uzbek's rich morphology, not a bug in the evaluation harness.

## Logging

Every stage logs through `app/utils/logger.py` to `logs/app.log` (and
stdout): ingestion, embedding, search, reranking, generation, and errors,
per the spec's "log everything" requirement. `LOG_LEVEL` in `.env`
controls verbosity.

## Error handling

Each layer defines its own typed exceptions rather than letting raw
library errors propagate: `VectorStoreError`/`BM25IndexError` for
corrupted or missing indexes (caught by `RAGPipeline` and
`IndexingPipeline`, which fall back to an empty index rather than
crashing), `DocumentLoadError` for broken/empty/undecodable source files
(caught by the Upload page, which restores the previous file on a failed
overwrite rather than leaving a broken file in place), `LLMConnectionError`
/`LLMModelNotFoundError` for an unreachable or unpulled Ollama model
(shown as a clear in-UI message, not a stack trace), and content-hash-based
deduplication so re-indexing an unchanged file is always a fast no-op.
